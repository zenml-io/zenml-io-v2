## Overview

Doctolib’s Consultation Template Manager (CTM) is a production conversational agent for configuring the templates used by the company’s existing Consultation Assistant, an ambient-scribing system that turns consented patient consultations into clinical notes. The underlying scribe could already adapt notes by country and specialty, but Doctolib found that individual practitioners still had different preferences for structure, style, and content. Manually authoring a high-quality template required time and technical skill that clinicians generally did not have. CTM addresses this problem through a conversational interface: a practitioner describes the desired note format, answers focused questions, refines a draft, or supplies an existing free-form template for conversion into an AI-ready template.

The notable LLMOps aspect is not simply the use of an LLM to generate a template. Doctolib reports that an existing internal AI platform made it possible to take the system from a March 2026 hackathon to production with external beta users in approximately three weeks. The platform supplied common orchestration, model access, deployment, session persistence, evaluation, monitoring, and production compute. This reduced the new team’s infrastructure work, while still leaving the product-specific agents, prompts, and evaluation cases to be designed and tested for CTM. The reported speed should therefore be understood as the result of platform reuse and a constrained initial release, not as evidence that any healthcare agent can safely be deployed in three weeks without comparable foundations and governance.

## Problem and product design

The Consultation Assistant generates a note from a clinical encounter, but its usefulness depends on whether the note matches the practitioner’s preferred way of working. Doctolib already supported consultation templates containing instructions about note format, style, and content. A well-designed template could eliminate rewriting, but creating one was a usability bottleneck. CTM turns template authoring into an agentic conversation rather than a conventional settings page.

The system supports three main user paths through a root orchestrator and specialist agents. An interviewer handles a blank-slate request by asking about specialty, consultation type, structure, and style before producing a first draft. A builder performs iterative refinement as the clinician requests changes such as adding an allergies section or shortening the output. A converter restructures an existing free-form practitioner template into a format suitable for use by the Consultation Assistant. The agents share two tools: one presents a multiple-choice question and another pushes a draft into the product editor. This tool design gives the application structured events that determine what the interface renders, rather than requiring the front end to infer intent from arbitrary text.

The resulting template contains bracketed instructional text that the downstream note-generation model follows. CTM is therefore an indirect control layer for another production LLM workflow: it does not primarily write the final clinical note, but creates the practitioner-specific instructions that influence future notes. The article states that the agent was initially released in France and Germany, with the same foundation intended for other European markets. It also describes possible future agents for letters and other template-driven documents, although those extensions are plans rather than demonstrated production results in this case.

## Agent and platform architecture

CTM was implemented as a small multi-agent workflow using Google’s Agent Development Kit (ADK), described in the source as an open framework for composing LLM agents. Doctolib’s in-house agentic framework built on ADK provides orchestration, tools, and response streaming. Prompt and runtime configuration are maintained as version-controlled files through an internal configuration system. This makes a prompt modification a reviewed code change and creates a clearer audit and rollback boundary than editing prompts directly in an unmanaged console.

Conversation state persists in Redis and Amazon S3. The article does not specify the exact division of responsibilities between the two stores, retention policies, encryption controls, access controls, or deletion behavior, so those details should not be inferred. The use of persistent session storage is nevertheless important for a multi-turn clinical-product interaction: the builder must retain enough conversational context to refine a template consistently across turns.

All LLM calls pass through a provider-agnostic gateway built on the open-source LiteLLM proxy. Doctolib says this abstraction allows underlying models to be changed without modifying application code, and that routing and fallback policies can direct requests to another model during a provider outage. The gateway also exposes dedicated production-grade model capacity that had already been secured for the broader AI platform. These properties address portability, resilience, and capacity provisioning, but the source does not provide latency, cost, availability, model identity, token usage, or fallback-quality measurements. Provider abstraction can also introduce operational complexity: different models may vary in tool-calling behavior, instruction following, language performance, and evaluation scores, so seamless technical switching does not guarantee equivalent product behavior.

## Delivery and deployment

The production path uses GitHub Actions, Docker, Kubernetes, Helm, and GitOps deployment through ArgoCD. CTM followed existing service patterns, with the team mainly choosing CTM-specific settings such as the model, session store, and resource limits. The article reports that the service reached staging the day after its code entered the main branch. This illustrates the value of a paved road: standardized build and deployment patterns turn infrastructure work into configuration and reviewed changes rather than a bespoke pipeline for every agent.

The feature was developed by one software engineer and one machine-learning engineer full time, with part-time product, design, and product-marketing support. Product iteration and engineering readiness happened in parallel. Internal healthcare professionals tested an alpha during the first week, and a Medical Excellence committee reviewed the product before release. The rollout then began with external beta practitioners, followed by gradual expansion while the team collected feedback and usage data. Doctolib says it expects online A/B testing to become the standard experimentation approach once the user base is sufficiently large.

This rollout sequence is a meaningful risk-control mechanism for a clinical workflow. It limits exposure while the team observes real usage and creates an opportunity to correct failures before broad availability. However, the source does not describe formal safety metrics, incident rates, human escalation procedures, privacy assessments, or the precise scope of the Medical Excellence review. The reported deployment process should therefore not be treated as a complete account of healthcare AI assurance.

## Evaluation and observability

Doctolib treats evaluation and monitoring as release prerequisites. Services connect to Datadog for metrics and alerting, while Braintrust supplies tracing and model-level evaluation. Scorer suites run when prompts change, and dashboards are used to identify regressions before they reach users. This is particularly relevant for an agent whose output is both a multi-turn conversation and a generated document: simple label accuracy would not adequately capture repeated questions, poor adaptation, missing sections, or an unusable final template.

The team built clinician personas and a model-based user simulator with Product and internal doctors. The simulator role-plays practitioners with specified specialties, goals, and personas, allowing the interviewer and builder to be exercised through complete multi-turn dialogues before release. Model-based scorers assess properties such as avoiding repeated questions, adapting to specialty, and producing a coherent template. The converter is evaluated primarily for faithfulness to the source template. Prompt changes rerun the evaluation suite, and failures become new test cases.

The article gives concrete examples of how this loop exposed weaknesses: the interviewer repeated questions across turns, the converter omitted sections from long templates, and specialty terminology confused the scorer. These examples show evaluation being used diagnostically rather than as a one-time benchmark. At the same time, model-based scoring and simulated practitioners are proxies. They may miss ambiguous clinical requirements, unusual user behavior, language-specific failures, or unsafe transformations. The source does not report scorer agreement with human reviewers, test-set size, thresholds for release, false-positive or false-negative rates, or whether production outputs undergo systematic human review. Those limitations matter when interpreting the claim that the system is reliable for clinical use.

## Results and tradeoffs

Doctolib reports access for approximately 6,000 practitioners during the early release. Of practitioners who began using CTM, 78% eventually saved a customized consultation template. Approximately nine out of ten saved templates were retained with minor edits or no edits, and about half of practitioners who tested the agent ultimately used their template in a real consultation summary, typically within a few days. These figures suggest that the conversational approach reduced the friction of template creation and that many generated templates were acceptable enough to be used operationally. They do not, by themselves, demonstrate improved clinical documentation quality, reduced documentation time, patient-safety benefits, or general performance across all specialties and markets.

The main architectural tradeoff is speed through standardization. A shared gateway, deployment path, tracing system, and evaluation harness let a small team focus on the agent and user experience. The cost is dependence on platform conventions and additional work whenever a new use case exposes assumptions that the platform was not designed to handle. Doctolib explicitly notes that unexpected issues should be budgeted for, with fixes improving the platform for subsequent projects.

A second tradeoff is the use of multiple agents and model-mediated evaluation. Specialist roles make the workflow easier to reason about and align with distinct user journeys, but orchestration adds routing failure modes, latency, model calls, and prompt-maintenance overhead. Persistent conversations improve usability but increase the importance of data governance and lifecycle controls, especially in healthcare. Provider portability improves resilience and bargaining flexibility, while model substitutions require regression testing for language, specialty, tool use, and template fidelity.

Overall, the case demonstrates a credible production pattern for a narrowly scoped healthcare agent: start from an existing product need, constrain the agent’s actions through explicit tools, version prompts as code, put models behind a gateway, deploy through a standardized GitOps path, evaluate multi-turn behavior offline, and roll out progressively. The strongest evidence in the source concerns delivery speed and early adoption. Claims about clinical quality, safety, and reliability remain limited by the absence of independently verified outcomes and detailed evaluation methodology.
