Pydantic AI brings the Pydantic team's approach to agents: typed dependencies, validated structured outputs, and a model-agnostic API that stays recognisably Python. If you want an agent whose output you can trust to match a schema, it is a very good choice.

ZenML is not a competing harness. It is the orchestration layer around the agent: your `Agent` runs unchanged inside a `@step`, and ZenML supplies the pipeline, the versioned artifacts, the cache, and the stack that puts it on Kubernetes, Vertex AI, SageMaker, or AzureML.

These compose cleanly because both are ordinary Python. Pydantic AI validates what comes out of the model. ZenML stores what comes out of the step, and remembers which run produced it.

  It is worth being precise about the split, because "agent framework" and "orchestrator" get used loosely enough that they sound like alternatives.

  <Fragment slot="bullets">
    - **Pydantic AI asks:** How do I define this agent, give it typed dependencies, call a model, and validate what comes back against a schema?
    - **ZenML asks:** This ran. What did it produce, where is that stored, which inputs made it, and do I have to compute it again?
    - **No overlap:** ZenML has no agent abstractions at all. It does not know what a tool call is, and it will not help you design one.

<FeatureWithGraphic title="What a pipeline adds on top" reverse={true}>
  <WhatZenMLAddsOnTop slot="graphic" />

  The agent code does not change. What changes is what exists around it after it runs.

  <Fragment slot="bullets">
    - **`@pipeline`:** Wraps the agent in a run with a status, a history, and steps you can inspect in the dashboard.
    - **Versioned artifacts:** Return `Annotated[Brief, "brief"]` and the validated Pydantic model is stored, versioned, and loadable by name across runs. The type survives the round trip.
    - **`enable_cache`:** Unchanged steps are served from cache on every run, so tuning the step after the agent does not re-invoke the agent.
    - **`zenml stack set`:** The same pipeline runs on Kubernetes, Vertex AI, SageMaker, or AzureML with no code change, and artifacts land in your own bucket.
  </Fragment>
</FeatureWithGraphic>

## Where they overlap, and where they do not

Both projects touch observability, and it is the one place a reader might reasonably expect a conflict. There is not one.

- **Logfire** traces what happened *inside* an agent run: the model calls, the tool calls, the timings. That is a level of detail ZenML does not capture and does not try to.
- **ZenML** records what happened *around* the step: which run, which inputs, which artifact version, on which stack. That is a level Logfire is not aiming at.
- Teams commonly run both, and they answer different questions during an incident.

## How the two surfaces map

| Concept | Pydantic AI | ZenML |
|---|---|---|
| Unit of work | `Agent.run()` | `@step` (the agent runs inside it) |
| Boundary | The agent and its dependencies | `@pipeline` |
| Typing | Validated structured output | `Annotated[T, "name"]` on the artifact |
| Outputs | `AgentRunResult` in memory | Versioned artifacts in your bucket |
| Avoiding repeat work | Not applicable | `enable_cache` across runs |
| Observability | Logfire traces inside the run | Runs, steps, and artifacts around it |
| Where it runs | Your process | Stack orchestrator (`zenml stack set`) |
| Serving | Your own wrapper | `zenml pipeline deploy --name ...` |

from pydantic import BaseModel
from pydantic_ai import Agent
from zenml import pipeline, step
from zenml.client import Client

class Brief(BaseModel):
    summary: str
    sources: list[str]

agent = Agent("anthropic:claude-sonnet-4-6", output_type=Brief)

@step
def gather_context(topic: str) -> Annotated[str, "context"]:
    return retrieve_documents(topic)

@step(enable_cache=False)
def run_agent(context: str, topic: str) -> Annotated[Brief, "brief"]:
    # The validated Pydantic model is stored as the artifact,
    # so the type survives the round trip.
    return agent.run_sync(f"{context}\\n\\nBrief on: {topic}").output

@step
def evaluate(brief: Brief) -> Annotated[dict, "scores"]:
    return score(brief.summary)

@pipeline
def brief_pipeline(topic: str):
    evaluate(run_agent(gather_context(topic), topic))

brief_pipeline("AI orchestration")

# Comes back typed, from any past run:
brief = Client().get_artifact_version("brief").load()`}

Build the agent with Pydantic AI, keep its typing and its tracing, and add ZenML when the agent becomes a workload: when the outputs need versioning, when re-running everything gets expensive, and when it has to run on your own infrastructure.
