CrewAI is a framework for building multi-agent systems: agents with roles and backstories, tasks with expected outputs, and Flows for when you need explicit control over the sequence. It is opinionated about how agents collaborate, and that opinion is the reason to pick it.

ZenML is not another opinion about agent collaboration. It is the orchestration layer around whatever you built. Your crew runs unchanged inside a `@step`, and ZenML supplies the pipeline around it: a run record, versioned artifacts in your own bucket, a cache that skips steps whose code and inputs did not change, and a stack that puts the whole thing on Kubernetes, Vertex AI, SageMaker, or AzureML.

The question CrewAI answers is how the agents work together. The question ZenML answers is what happened when they did, and what it costs to do it again.

<FeatureWithGraphic title="Orchestration around the agent stack">
  <RuntimeLayer slot="graphic" />

  The two live at different levels. A crew is a program; a pipeline is the thing that runs programs and remembers what they did.

  <Fragment slot="bullets">
    - **No rewrite:** `crew.kickoff()` goes inside a `@step`. Your agents, tasks, and tools are untouched.
    - **What ZenML owns:** The run record, the artifacts, the cache, and the deployment target. Not the agent logic.
    - **What CrewAI keeps owning:** Roles, delegation, task routing, and the collaboration model. ZenML has no opinion about any of it.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Re-running without re-paying" reverse={true}>
  <CachedRerun slot="graphic" />

  A crew that makes a dozen LLM calls is expensive to run and more expensive to run repeatedly while you tune the step after it. Re-running should not mean re-paying for the part you did not touch.

  <Fragment slot="bullets">
    - **Cache key:** ZenML hashes a step's code, inputs, and parameters. If nothing changed, the stored artifact is returned and the step body never executes.
    - **In practice:** In a pipeline that prepares context, runs the crew, then evaluates the output, editing only the evaluation re-runs only the evaluation. The crew call is served from cache.
    - **The exception:** Mark the crew step `@step(enable_cache=False)` when you want it to execute every time, and keep the cache on the deterministic steps around it.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Your own cloud, your own bucket">
  <SelfHostedRuntime slot="graphic" />

  CrewAI offers a managed platform for deploying and monitoring crews. ZenML's answer to the same question is the stack, and the difference that matters is where the data ends up.

  <Fragment slot="bullets">
    - **Stack components:** An orchestrator plus an artifact store, registered once with `zenml stack register`, then used by every pipeline.
    - **Switching:** `zenml stack set sagemaker` repoints the same code from a local orchestrator to Kubernetes, Vertex AI, SageMaker, or AzureML.
    - **Where data lives:** Artifacts land in your own S3, GCS, or Azure Blob bucket. Self-host the server and nothing about a run leaves your infrastructure.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="One pipeline, whichever framework each team picked" reverse={true}>
  <HarnessFreedom slot="graphic" />

  Most organisations do not standardise on one agent framework. One team is on CrewAI, another on Pydantic AI, a third calls the OpenAI Agents SDK directly. ZenML sits under all of them because a step is just Python.

  <Fragment slot="bullets">
    - **No adapter needed:** Whatever the framework, the call goes in a step and the return value becomes an artifact.
    - **One record:** Runs from every team land in the same server, with the same artifact and lineage model.
    - **The trade:** ZenML gives you nothing framework-specific in return. It does not know what a crew is, and it will not help you design one.
  </Fragment>
</FeatureWithGraphic>

## How the two surfaces map

| Concept | CrewAI | ZenML |
|---|---|---|
| Unit of work | Task, executed by an Agent | `@step` (the crew runs inside it) |
| Boundary | `Crew` / `Flow` | `@pipeline` |
| Control flow | Sequential or hierarchical process | The pipeline graph |
| Outputs | `CrewOutput` returned in memory | Versioned artifacts in your bucket |
| Avoiding repeat work | Re-run starts from the top | `enable_cache` across runs |
| Where it runs | Your process, or CrewAI's platform | Stack orchestrator (`zenml stack set`) |
| Cross-run reuse | Bring your own store | `get_artifact_version(...).load()` |
| Serving | Your own wrapper, or the platform | `zenml pipeline deploy --name ...` |

from zenml import pipeline, step

@step
def gather_context(topic: str) -> Annotated[str, "context"]:

# Non-deterministic, so it always executes; the steps around

@step(enable_cache=False)
def run_crew(context: str, topic: str) -> Annotated[str, "draft"]:
    researcher = Agent(role="Researcher", goal=f"Research {topic}")
    writer = Agent(role="Writer", goal="Write a brief")
    crew = Crew(
        agents=[researcher, writer],
        tasks=[
            Task(description=context, agent=researcher,
                 expected_output="notes"),
            Task(description="Write it up", agent=writer,
                 expected_output="a brief"),
        ],
    )
    return str(crew.kickoff())

@step
def evaluate(draft: str) -> Annotated[dict, "scores"]:
    return score(draft)

@pipeline
def crew_pipeline(topic: str):
    evaluate(run_crew(gather_context(topic), topic))

crew_pipeline("AI orchestration")
