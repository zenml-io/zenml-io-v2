DBOS is a durable execution library rather than a platform. You add decorators to ordinary Python or TypeScript functions, it checkpoints workflow state into Postgres, and a crashed process picks up where it left off. There is no separate orchestrator to run: the durability lives in a library and a database you already operate. For transactional application workflows, that is a genuinely light footprint.

ZenML answers a different question. It is the orchestration layer for AI workloads written in Python, where the thing you care about is not only that a process survived, but what it produced: which artifact came from which run, from which inputs, under which version of the code. Steps write versioned artifacts, unchanged steps are served from cache instead of re-running, and the same pipeline moves between Kubernetes, Vertex AI, SageMaker, and AzureML by swapping a stack.

Put plainly: DBOS remembers where a workflow got to. ZenML remembers what a pipeline produced.

<FeatureWithGraphic title="The step is the unit of record">
  <StepRecord slot="graphic" />

  In DBOS, the unit is the workflow step, and what persists is the state needed to resume it. In ZenML, the unit is the `@step`, and what persists is what the step produced: its return value, stored in the artifact store, versioned, and attached to the run.

  <Fragment slot="bullets">
    - **What is stored:** DBOS checkpoints step state to Postgres so execution can resume. ZenML stores the step's output as an artifact in your bucket (S3, GCS, Azure Blob) and records the run metadata in the ZenML server.
    - **Naming:** Return `Annotated[str, "brief"]` and the artifact is addressable by name across runs rather than by an opaque id.
    - **Metadata:** ZenML has no LLM-specific primitive. What it gives you is a place to put the numbers: `log_metadata()` attaches token counts, cost, or anything else to the step, and it shows up on the run beside the artifact.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Artifact versioning across every step" reverse={true}>
  <ArtifactVersioning slot="graphic" />

  A Postgres checkpoint table tells you a workflow completed. It does not tell you that this run's embeddings differ from last week's, or let you pull last week's back out. ZenML versions every step output, so a run is a set of inspectable, retrievable artifacts rather than a log line.

  <Fragment slot="bullets">
    - **Versions:** Re-run a step with changed inputs and you get a new version of the same named artifact, not an overwrite. Both stay retrievable.
    - **Cross-run load:** A later run, or a notebook, can pull an earlier run's output by name with `get_artifact_version(...).load()` on the ZenML client.
    - **Comparison:** Two runs of the same pipeline can be compared in the dashboard on what they produced, which is the question you actually ask after a model or prompt change.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="One stack, four clouds">
  <StackDeployment slot="graphic" />

  DBOS runs wherever your service runs, and DBOS Cloud hosts it for you. Its footprint is deliberately small: a library plus Postgres. ZenML's equivalent lever is the stack, which is where its opinion sits.

  <Fragment slot="bullets">
    - **Stack components:** An orchestrator plus an artifact store, and whatever else the workload needs. Configure it once with `zenml stack register`, and every pipeline uses it.
    - **Switching:** `zenml stack set sagemaker` repoints the same pipeline code from a local orchestrator to Kubernetes, Vertex AI, SageMaker, or AzureML. No code change, no redeploy of a service.
    - **Where data lives:** Artifacts land in your own bucket. Self-host the server and nothing about a run leaves your infrastructure.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Deploy a pipeline and call it by name" reverse={true}>
  <NamedDeployments slot="graphic" />

  Both let you turn code into something callable. The difference is what you get back when it runs.

  <Fragment slot="bullets">
    - **Serving:** `zenml pipeline deploy run.weather_agent --name weather-agent-service` stands the pipeline up behind an HTTP endpoint.
    - **Per-request lineage:** Every request to that endpoint is a ZenML run, so the artifacts, metadata, and step history exist for a single call the same way they do for a batch job.
    - **DBOS:** Durable workflows are invoked from inside your own service, which keeps the footprint smaller but leaves the run record to you.
  </Fragment>
</FeatureWithGraphic>

## How the two surfaces map

| Concept | DBOS | ZenML |
|---|---|---|
| Workflow boundary | `@DBOS.workflow` | `@pipeline` |
| Unit of work | `@DBOS.step` | `@step` |
| What persists | Workflow state in Postgres | Step outputs as versioned artifacts |
| Skipping completed work | Checkpoint resume after a crash | `enable_cache` on every run |
| Durable pause | Durable sleep and queues | Not supported |
| Where it runs | Inside your service, or DBOS Cloud | Stack orchestrator (`zenml stack set`) |
| Cross-run reuse | Bring your own store | `get_artifact_version(...).load()` |
| Serving | Invoke from your own service | `zenml pipeline deploy --name ...` |

<ComparisonCta headline={frontmatter.ctaHeading}>
If you want crash-proof application workflows with the smallest possible footprint, and you already run Postgres, DBOS is a clean answer. If the work is a Python AI pipeline where you care about which version of an artifact came from which run, and about running the same code on Kubernetes today and Vertex AI next quarter, ZenML is the layer you want underneath it.
</ComparisonCta>
