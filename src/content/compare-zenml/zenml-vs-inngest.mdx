Inngest is an event-driven durable functions platform. You send events, functions react to them, and each `step.run` is memoized so a retry does not repeat completed work. It gives you sleeps that release compute, waits on future events, throttling and concurrency controls, and SDKs across TypeScript, Python, and Go. For application workflows driven by events, that is a well-shaped platform.

ZenML sits at a different layer. It orchestrates Python AI workloads as pipelines of steps, and it is organised around the artifact rather than the event. A step's return value is stored and versioned in your own bucket, unchanged steps are served from cache rather than re-executed, and the same pipeline runs on Kubernetes, Vertex AI, SageMaker, or AzureML by swapping a stack.

Both memoize completed work. The difference is what survives afterwards: Inngest keeps the step result so the run can continue, ZenML keeps it so you can go back and ask what a run produced.

<FeatureWithGraphic title="Pipelines you own vs functions the platform drives">
  <RuntimeUnderHarness slot="graphic" />

  Inngest's model inverts control: your functions are registered, and the Inngest platform decides when to invoke each step, tracking progress on its side. ZenML's model keeps the pipeline as a program you run, with a stack orchestrator executing it and a server recording what happened.

  <Fragment slot="bullets">
    - **Who drives:** Inngest calls back into your app step by step. ZenML submits the pipeline to the orchestrator in your stack (Kubernetes, Vertex AI, SageMaker, AzureML, Airflow, Kubeflow) and records the run.
    - **Where the record lives:** Inngest's run history lives in the Inngest platform. ZenML's lives in a server you can self-host, with artifacts in your own bucket.
    - **What you adopt:** Inngest is a platform your application routes work through. ZenML is a library your pipelines are written in.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Pipeline primitives vs polyglot durable functions" reverse={true}>
  <AgentPrimitives slot="graphic" />

  Inngest's primitives are shaped for applications and span three languages. ZenML's are shaped for Python pipelines and stop at the boundary of the language, which is the trade it makes deliberately.

  <Fragment slot="bullets">
    - **`@step` / `@pipeline`:** Ordinary Python functions. No determinism constraint on the body, and the return value is captured as a versioned artifact.
    - **`enable_cache`:** Unchanged code and inputs are served from cache on every run, not only on a retry.
    - **`StepRetryConfig`:** Per-step retries with delay and backoff. Inngest gives you more here: sleeps, waits on events, throttling, and concurrency keys have no ZenML equivalent.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Where your data actually sits">
  <CustomerDataPath slot="graphic" />

  For AI workloads the intermediate values are the sensitive part: prompts, retrieved documents, customer records, model outputs. Where those live is a procurement question as much as a technical one.

  <Fragment slot="bullets">
    - **ZenML:** Artifacts are written to your artifact store, which is your S3, GCS, or Azure Blob bucket. Self-host the server and the run metadata stays with you too.
    - **Inngest:** Step outputs pass through the Inngest platform as part of how the run is coordinated. Inngest offers self-hosting, and the managed cloud is the default path.
    - **Why it matters:** In a regulated environment the difference between "our bucket" and "a vendor's coordination layer" tends to decide the review.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Versioned artifacts vs event-sourced steps" reverse={true}>
  <ArtifactLineage slot="graphic" />

  Both keep a record of a run. Inngest's is an event stream of what the platform did. ZenML's is a set of artifacts you can open.

  <Fragment slot="bullets">
    - **Versions:** Re-run a step with changed inputs and you get a new version of the same named artifact rather than an overwrite. Both remain retrievable.
    - **Cross-run load:** `get_artifact_version(...).load()` pulls an earlier run's output into a notebook or a later pipeline, by name.
    - **Serving:** `zenml pipeline deploy` stands a pipeline up behind an endpoint, and every request becomes a run with the same artifacts and lineage as a batch job.
  </Fragment>
</FeatureWithGraphic>

## How the two surfaces map

| Concept | Inngest | ZenML |
|---|---|---|
| Workflow boundary | `inngest.create_function` | `@pipeline` |
| Unit of work | `step.run` (memoized) | `@step` (cached, versioned output) |
| Trigger | An event you send | An invocation, schedule, or deployment |
| Skipping completed work | Step memoization within a run | `enable_cache` across runs |
| Durable pause | `step.sleep`, `step.wait_for_event` | Not supported |
| Where it runs | Your app, driven by the platform | Stack orchestrator (`zenml stack set`) |
| Outputs | Step results in run history | Versioned artifacts in your bucket |
| Cross-run reuse | Bring your own store | `get_artifact_version(...).load()` |

<ComparisonCta headline={frontmatter.ctaHeading}>
If your workflows are event-driven and the hard parts are waits, fan-out and flow control across more than one language, Inngest is the platform to adopt. If the work is a Python AI pipeline where you care about which artifact came from which run, about not re-paying for steps that did not change, and about keeping all of it in your own infrastructure, ZenML is the layer you want underneath it.
</ComparisonCta>
