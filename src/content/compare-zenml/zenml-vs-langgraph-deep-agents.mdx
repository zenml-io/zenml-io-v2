LangGraph models an agent as a graph: nodes, edges, and state that persists across steps, with checkpointers for durability and Deep Agents layering planning and sub-agents on top. Behind it sits a packaged path to production through LangGraph Platform and LangSmith, which handles deployment, persistence, and observability for you.

That packaging is the real decision. Adopting the graph is one commitment; adopting the platform underneath it is a much larger one, and the two arrive together. ZenML offers the second half separately: keep the graph, and run it as a step inside a pipeline you orchestrate on your own infrastructure, with artifacts in your own bucket and run metadata in a server you can self-host.

If you are weighing LangGraph purely as a way to build agents, the [ZenML vs LangGraph](/compare/zenml-vs-langgraph) comparison covers that. This page is about the deployment and ownership question.

<FeatureWithGraphic title="Self-hosted vs packaged">
  <SelfHostVsPackaged slot="graphic" />

  Both give you a route from a working agent to something running in production. They differ in who operates it and where the data sits.

  <Fragment slot="bullets">
    - **ZenML:** A server you deploy (Helm chart or ZenML Pro), an artifact store that is your own S3, GCS, or Azure Blob bucket, and an orchestrator that is your existing Kubernetes, Vertex AI, SageMaker, or AzureML.
    - **LangGraph Platform:** Deployment, persistence, and scaling as a managed product, with self-hosted tiers available on the paid plans.
    - **The trade:** The packaged path is faster to production and gives you graph-aware features ZenML has no equivalent for. The self-hosted path keeps prompts, retrieved documents, and model outputs inside your own account.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Where the sensitive values live" reverse={true}>
  <SandboxSecurity slot="graphic" />

  For agent workloads the intermediate values are the sensitive part: prompts, retrieved documents, customer records, model outputs. Where those are written tends to decide a security review.

  <Fragment slot="bullets">
    - **Artifacts:** ZenML writes every step output to your artifact store. Nothing about a run's contents leaves your infrastructure when the server is self-hosted.
    - **Credentials:** Model keys stay in your own execution environment. ZenML has no LLM primitive and never brokers a provider call.
    - **What ZenML does not give you:** No sandboxing, and no tool-permission model. If the agent runs untrusted code, that isolation is on you or on the harness.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Versioned runs and deployments">
  <VersionedDeployments slot="graphic" />

  Both let you put a version of an agent behind an endpoint. What differs is what you get back per call.

  <Fragment slot="bullets">
    - **Artifacts per run:** Every step output is stored, versioned, and loadable by name with `get_artifact_version(...).load()`, so a change to a prompt is visible as a new artifact version rather than a new log line.
    - **Serving:** `zenml pipeline deploy run.agent_pipeline --name agent-service` stands the pipeline up behind an endpoint, and every request is a run with the same artifacts and lineage as a batch job.
    - **Caching:** Unchanged steps are served from cache on every run, which matters most when you are iterating on the step after the agent.
  </Fragment>
</FeatureWithGraphic>

## Being honest about the gap

LangGraph has a set of features ZenML does not attempt, and a fair comparison should name them.

- **Graph semantics.** Branching, cycles, and conditional edges are LangGraph's model. A ZenML pipeline is a DAG of steps; it does not loop.
- **Persisted graph state, interrupts, and time travel.** Checkpointers let a graph pause mid-execution, be inspected, resumed, and rewound to an earlier state. ZenML has no equivalent, and step caching is not one.
- **Deep Agents patterns.** Planning, sub-agents, and file-system tooling are harness concerns. ZenML orchestrates whatever you build; it does not help you build it.

What ZenML gives you in exchange is narrower and differently valuable: artifacts you own, caching across runs, and one orchestration layer that works the same whether the team picked LangGraph, CrewAI, Pydantic AI, or the OpenAI SDK.

## How the two surfaces map

| Concept | LangGraph & Deep Agents | ZenML |
|---|---|---|
| Unit of work | Graph node | `@step` (the graph runs inside it) |
| Boundary | `StateGraph` | `@pipeline` |
| Control flow | Edges, conditional edges, cycles | A DAG of steps, no loops |
| State | Persisted graph state via checkpointers | Versioned artifacts in your bucket |
| Pause and resume | Interrupts, time travel | Not supported |
| Avoiding repeat work | Checkpointer resume | `enable_cache` across runs |
| Where it runs | Your process, or LangGraph Platform | Stack orchestrator (`zenml stack set`) |
| Serving | LangGraph Platform | `zenml pipeline deploy --name ...` |
