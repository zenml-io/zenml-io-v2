ZenML and the Claude Agent SDK are not alternatives. The Agent SDK builds agents that read files, run commands, search the web, and edit code inside a session you start. It is a very good way to write the agent itself.

ZenML is the orchestration layer you put around that work when it stops being a session and becomes a workload. The agent code stays exactly as you wrote it, running inside a `@step`. What ZenML adds is everything around the call: the run record, the versioned artifacts, the cache that stops you paying twice for work that did not change, and a stack that puts the whole thing on Kubernetes, Vertex AI, SageMaker, or AzureML without a rewrite.

For a one-off task at your keyboard, you do not need any of that. For a hundred runs a day whose outputs someone will ask about next month, you do.

## What a pipeline adds around the agent

The Agent SDK gives you a session. A ZenML pipeline gives that session a place in a system of record.

- **The run:** Wrapping the agent call in a `@step` inside a `@pipeline` makes each execution a run with a start, an end, a status, and a history you can open in the dashboard.
- **Versioned artifacts:** Whatever the step returns is stored in your artifact store, versioned, and addressable. Return `Annotated[str, "patch"]` and the output is retrievable by name across runs rather than buried in a session log.
- **Metadata:** ZenML has no LLM-specific primitive, and it does not try to parse what the SDK did. It gives you a place to put what you care about: `log_metadata()` attaches token counts, cost, or tool-call counts to the step.

## Not re-paying for work that did not change

The Agent SDK writes session history to disk and can rewind file edits. That is useful while you are working, but it is not a cache across runs.

- **The cache key:** ZenML hashes a step's code, inputs, and parameters. If nothing changed, the stored artifact is returned and the body never executes.
- **What that means in practice:** In a pipeline that retrieves context, runs the agent, then evaluates the result, editing only the evaluation step re-runs only the evaluation step. The retrieval and the agent call are served from cache.
- **Turning it off:** A step that must always execute takes `@step(enable_cache=False)`, which is the right setting for the agent step itself whenever non-determinism is the point.

## Your infrastructure, your data

- **Where it runs:** `zenml stack set` repoints the same pipeline from your laptop to Kubernetes, Vertex AI, SageMaker, or AzureML. The agent code does not change.
- **Where artifacts land:** Your own S3, GCS, or Azure Blob bucket. Self-host the ZenML server and the run metadata stays with you too.
- **Serving:** `zenml pipeline deploy` stands the pipeline up behind an endpoint, and every request becomes a run with the same artifacts and lineage as a batch job.

## What ZenML does not do

Worth saying plainly, because it decides whether you need both.

- ZenML has **no sandbox and no tool-permission model**. The Agent SDK's isolation, allowed-tools configuration, and file-edit rewind have no ZenML equivalent, and you should keep using them.
- ZenML has **no durable wait**. If the agent needs to pause for a human for two days without holding compute, neither of these tools is the answer; a durable execution engine is.
- ZenML does **not** make a crashed step resume mid-execution. It re-runs the pipeline and serves the completed steps above the failure from cache, which gets you the cost saving but is not the same mechanism.

## How the two surfaces map

| Concept | Claude Agent SDK | ZenML |
|---|---|---|
| Unit of work | An agent session | `@step` (the session runs inside it) |
| Boundary | The task you give the agent | `@pipeline` |
| History | Session transcript on disk | Runs, steps, and artifacts in the server |
| Outputs | Files the agent edited | Versioned artifacts in your bucket |
| Avoiding repeat work | Prompt caching, file-edit rewind | `enable_cache` across runs |
| Where it runs | Wherever you start the session | Stack orchestrator (`zenml stack set`) |
| Serving | Your own wrapper | `zenml pipeline deploy --name ...` |
| Cross-run reuse | Not applicable | `get_artifact_version(...).load()` |
