The OpenAI Agents SDK is a deliberately small framework: agents with instructions and tools, handoffs between them, guardrails on inputs and outputs, and sessions that carry conversation history. It stays out of your way, and for building the agent itself that restraint is the point.

The restraint is also why teams reach for something else once the agent stops being a script. The SDK runs your agent; it does not decide where the run is recorded, what happened to the output, or how you avoid paying for the same work twice. ZenML is the orchestration layer that answers those: your `Runner.run()` goes inside a `@step`, and the pipeline around it gives you a run record, versioned artifacts in your own bucket, a cache keyed on code and inputs, and a stack that targets Kubernetes, Vertex AI, SageMaker, or AzureML.

<FeatureWithGraphic title="Re-running without starting from step one">
  <CachedRerun slot="graphic" />

  A multi-step agent pipeline that crashes at the end is expensive to restart, and so is tuning the last step while the first three keep re-executing.

  <Fragment slot="bullets">
    - **Cache key:** ZenML hashes a step's code, inputs, and parameters. If nothing changed, the stored artifact is returned and the body never executes, so a re-run after a failure does not re-pay for the completed steps above it.
    - **Not crash recovery:** Worth being exact. ZenML does not resume a pipeline mid-step the way a durable execution engine does. It re-runs, and the cache is what makes that cheap.
    - **The agent step:** Mark it `@step(enable_cache=False)` when it must execute every time, and keep the cache on the deterministic steps around it.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Artifacts you can open, not just traces of what happened" reverse={true}>
  <ArtifactLineage slot="graphic" />

  The SDK's tracing shows you the shape of a run: which agent ran, which tools were called, where a handoff happened. That is the right tool for debugging a single run. It is not a store of what the run produced.

  <Fragment slot="bullets">
    - **Artifacts:** Every step output is written to your artifact store, versioned, and attached to the run. Name it with `Annotated[str, "draft"]` and it becomes addressable across runs.
    - **Cross-run load:** `get_artifact_version(...).load()` on the ZenML client pulls any earlier run's output into a notebook or a later pipeline.
    - **Serving:** `zenml pipeline deploy` stands the pipeline up behind an endpoint, and every request becomes a run with the same artifacts and lineage as a batch job.
  </Fragment>
</FeatureWithGraphic>

## What neither of these does

The v1 version of this page argued for durable, compute-free waits on human approval. That is worth correcting rather than quietly dropping, because it is a real gap.

ZenML has **no durable wait primitive**. If your agent must pause for a human for hours or days without holding a process open, neither ZenML nor the Agents SDK solves it. A durable execution engine does, and Temporal, Restate, DBOS, and Inngest all have a genuine answer. ZenML sits alongside that rather than replacing it.

## How the two surfaces map

| Concept | OpenAI Agents SDK | ZenML |
|---|---|---|
| Unit of work | `Runner.run()` | `@step` (the agent runs inside it) |
| Boundary | An agent and its handoffs | `@pipeline` |
| Validation | Input and output guardrails | Artifact types on the step signature |
| Outputs | `RunResult` in memory | Versioned artifacts in your bucket |
| Avoiding repeat work | Not applicable | `enable_cache` across runs |
| Observability | Traces of a single run | Runs, steps, and artifacts across runs |
| Where it runs | Your process | Stack orchestrator (`zenml stack set`) |
| Serving | Your own wrapper | `zenml pipeline deploy --name ...` |

from agents import Agent, Runner
from zenml import pipeline, step
from zenml.client import Client

researcher = Agent(name="Researcher", instructions="Research the topic.")
writer = Agent(name="Writer", instructions="Write a brief.")

@step
def gather_context(topic: str) -> Annotated[str, "context"]:
    return retrieve_documents(topic)

@step(enable_cache=False)
def run_agent(context: str, topic: str) -> Annotated[str, "draft"]:
    result = Runner.run_sync(
        researcher, f"{context}\\n\\nTopic: {topic}"
    )
    return str(Runner.run_sync(writer, result.final_output).final_output)

@step
def evaluate(draft: str) -> Annotated[dict, "scores"]:
    return score(draft)

@pipeline
def agent_pipeline(topic: str):
    evaluate(run_agent(gather_context(topic), topic))

agent_pipeline("AI orchestration")

# Edit evaluate() and re-run: gather_context is cached.
Client().get_artifact_version("draft").load()

# Same code on your cloud:

<ComparisonCta headline={frontmatter.ctaHeading}>
Keep the OpenAI Agents SDK for building the agent: the handoffs, the guardrails, the tools. Add ZenML when it becomes a workload rather than a script, when someone needs to know what a run produced, and when it has to run on your own infrastructure with the outputs stored somewhere you control. If you also need durable waits, put a durable execution engine underneath both.
