Hatchet is a distributed task queue with durable execution on top, backed by Postgres. It gives you workers, queues, concurrency and rate-limit controls, cron scheduling, fan-out, and a dashboard for the whole fleet. If your problem is throughput and reliability across a lot of heterogeneous background work, that is a strong platform to adopt.

ZenML is narrower and differently shaped. It orchestrates AI workloads written in Python as pipelines of steps, and the thing it is built around is the output rather than the queue. Every step's return value becomes a versioned artifact, unchanged steps are served from cache rather than re-executed, and the same pipeline runs on Kubernetes, Vertex AI, SageMaker, or AzureML by swapping a stack.

The two are not really competing for the same slot. Hatchet decides how work gets scheduled and retried across your infrastructure. ZenML decides what a run of an AI pipeline is, what it produced, and how you get that back.

<FeatureWithGraphic title="Pipeline orchestration vs task orchestration">
  <RuntimeVsPlatform slot="graphic" />

  Hatchet's model is tasks and workers: you register functions, workers pull from queues, and the platform handles retries, concurrency, and scheduling. ZenML's model is a pipeline of typed steps whose outputs are persisted and connected.

  <Fragment slot="bullets">
    - **Unit of work:** A Hatchet task is a unit of scheduling. A ZenML `@step` is a unit of record, whose return value is stored and versioned.
    - **What the platform owns:** Hatchet owns dispatch, concurrency, and rate limits. ZenML delegates execution to a stack orchestrator (which can be Kubernetes, Vertex AI, SageMaker, AzureML, Airflow, or Kubeflow) and owns the run and artifact metadata.
    - **Adoption shape:** Hatchet is a platform you run and route work through. ZenML is a library you write pipelines in, plus a server that records them.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="The step is the captured unit" reverse={true}>
  <LlmLineage slot="graphic" />

  In an AI pipeline the expensive step is a training run or a batch of LLM calls, and the question afterwards is what it produced. Hatchet records that a task succeeded and what it returned into the run's event history. ZenML records the return value itself, as an artifact you can go and load.

  <Fragment slot="bullets">
    - **Artifacts:** Every step output is stored in your artifact store, versioned, and attached to the run. Name it with `Annotated[str, "brief"]` and it becomes addressable across runs.
    - **Metadata:** ZenML has no LLM-specific primitive. It gives you the place to put the numbers: `log_metadata()` attaches token counts, cost, or model identity to the step, and they show up beside the artifact.
    - **Retrieval:** `get_artifact_version(...).load()` on the ZenML client pulls any earlier run's output back into a notebook or a later pipeline.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Where the cache boundary falls">
  <CacheBoundary slot="graphic" />

  Change one step in the middle of a pipeline and re-run it. What happens to the steps above it decides how fast you can iterate and how much you pay to do it.

  <Fragment slot="bullets">
    - **ZenML:** The cache key is the step's code, inputs, and parameters. Edit `draft` and re-run: `research` above it is served from cache and never executes, `draft` and everything downstream of it re-runs against the new value.
    - **Hatchet:** Re-running a workflow starts it again. Skipping completed work is something you build inside task bodies, against your own store.
    - **When it applies:** ZenML's caching is not a recovery mechanism. It applies on every run, including the ordinary case where you edited one step and re-ran the file.
  </Fragment>
</FeatureWithGraphic>

## How the two surfaces map

| Concept | Hatchet | ZenML |
|---|---|---|
| Workflow boundary | Workflow definition | `@pipeline` |
| Unit of work | Task (queued, retried) | `@step` (ordinary Python) |
| What persists | Run and task event history | Step outputs as versioned artifacts |
| Skipping completed work | Durable resume after failure | `enable_cache` on every run |
| Scheduling | Cron, events, queues | Delegated to the stack orchestrator |
| Concurrency control | Concurrency and rate-limit keys | Delegated to the stack orchestrator |
| Where it runs | Hatchet workers you deploy | Stack orchestrator (`zenml stack set`) |
| Cross-run reuse | Bring your own store | `get_artifact_version(...).load()` |

hatchet = Hatchet()

@hatchet.workflow(on_events=["review:create"])
class ReviewWorkflow:

    @hatchet.step(retries=3)

        topic = ctx.workflow_input()["topic"]

<ComparisonCta headline={frontmatter.ctaHeading}>
If the hard part is throughput, queueing, and keeping a large fleet of background tasks reliable, Hatchet is the platform to adopt. If the hard part is knowing what an AI pipeline produced, not paying twice for steps that did not change, and running the same code on four clouds, ZenML is the layer you want underneath it. Plenty of teams end up with both.
</ComparisonCta>
