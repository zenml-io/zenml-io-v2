CrewAI and Kitaru solve different problems at different layers. CrewAI is an **agent harness**: model your agents as a crew of roles, give each one a task, and let `crew.kickoff()` coordinate the work. AMP wraps the whole thing in a managed platform on top. If your problem is shaped like teamwork and role-based delegation, CrewAI is built for that.

Kitaru is a **replay-based eval layer**: it records every run as a session, and a session re-executes &mdash; unchanged for a faithful baseline, or forked with one thing changed. There&rsquo;s no first-class CrewAI adapter yet, so the honest path in is to import the traces you already collect (Langfuse, LangSmith, Braintrust, or OTel) &mdash; an [imported session](https://docs.zenml.io/kitaru) replays and evaluates exactly like a recorded one. If you want native recording, the fastest path is a project-local adapter built with the `kitaru-adapter-builder` agent skill; it lives in your repo, not ours.

<FeatureWithGraphic title="Different questions, different layers">
  <RuntimeLayer slot="graphic" />

  CrewAI is asking: how do I model a team of agents that collaborate on a task? Kitaru is asking: once that crew ships, which of its runs can I re-run? Import its traces, replay them, and see what a change actually did.

  <Fragment slot="bullets">
    - Kitaru doesn&rsquo;t compete for the harness layer. It has no opinion on roles, tasks, or delegation &mdash; that&rsquo;s CrewAI&rsquo;s job.
    - A CrewAI rollout looks like modeling agents as a crew. A Kitaru rollout looks like importing the traces the crew already produces, or building a small project-local adapter against the recording API.
    - The kickoff result &mdash; and the trace behind it &mdash; becomes a session you can replay with tool calls answered from the recording, or fork with one variable changed.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="No adapter? Three honest ways in." reverse={true}>
  <CheckpointReplay slot="graphic" />

  There&rsquo;s no first-class CrewAI adapter today, and Kitaru would rather say that plainly than fake one. Three paths in, in order of cost: import the traces you already collect (Langfuse, LangSmith, Braintrust, or OTel) &mdash; the cheapest, and an imported session replays and evaluates exactly like a recorded one. Build a project-local adapter against the recording API if you want native capture &mdash; the `kitaru-adapter-builder` skill generates the smallest one that works and tells you what it can and can&rsquo;t see. Or, if the crew runs somewhere you can&rsquo;t wrap, register it as a function and let Kitaru call your system instead.

  <Fragment slot="bullets">
    - **Import.** `kitaru session import crew-trace.jsonl --importer kitaru/langfuse@latest --agent crew@latest --wait` &mdash; no code change, no adapter, sessions land exactly like a native recording.
    - **Project-local adapter.** Ordinary code that calls the recording API and lives in your repo. Wrap the public `crew.kickoff()` entrypoint, change nothing else &mdash; a recording that changes behavior isn&rsquo;t a recording.
    - **Function agent.** When the crew runs somewhere you don&rsquo;t control, register it as a function; Kitaru calls it, and the session adopts once you import the result.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Self-hosted, on your own cloud">
  <SelfHostedRuntime slot="graphic" />

  CrewAI AMP is a managed agent platform with a hosted control plane. If you want the platform handled for you, that&rsquo;s a real value proposition. Kitaru takes the opposite trade: one self-hosted FastAPI + Postgres server, workers that execute replays and evaluations inside your environment, and sessions that never have to leave your systems.

  <Fragment slot="bullets">
    - **Self-hosted, Apache 2.0.** One server, run it however you run services today.
    - **Workers in your environment.** Replays, imports, and evaluations execute where you deploy them &mdash; your traces and credentials don&rsquo;t leave your systems.
    - **Beside your observability, not instead of it.** Langfuse, LangSmith, and Braintrust remain where you watch production; Kitaru is where you re-run it.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Bring-your-own harness vs CrewAI abstractions" reverse={true}>
  <HarnessFreedom slot="graphic" />

  CrewAI asks engineers to model their agents inside its building blocks. Kitaru asks for a trace. The harness underneath a session can be CrewAI, Pydantic AI, the OpenAI Agents SDK, or hand-written Python &mdash; Kitaru mostly cares whether it can see a recording, not how you produced it.

  <Fragment slot="bullets">
    - **Native or imported.** Pydantic AI, the OpenAI Agents SDK, LangGraph, Mastra, and the Vercel AI SDK have a first-class adapter. CrewAI doesn&rsquo;t yet &mdash; import its traces, or build a project-local adapter against the recording API.
    - **No graph DSL.** Whatever the harness decides &mdash; task delegation, tool calls, conditional branches &mdash; Kitaru records the result rather than re-implementing the decision logic.
    - **Different harnesses, one eval layer.** When different teams pick different harnesses, one place to record and replay is a smaller ask than one harness across the org.
  </Fragment>
</FeatureWithGraphic>

## How the two surfaces map

| Concept | CrewAI | Kitaru |
|---|---|---|
| Layer | Agent harness (how the crew collaborates) | Replay-based evals (how you test what it did) |
| Core unit | Crew run (`kickoff`) | Session &mdash; recorded model and tool calls, re-executable |
| Composition | Standalone framework, AMP on top | Imported trace, or a project-local adapter |
| Tool calls in tests | Hit real systems, or you mock them by hand | Answered from the recording per tool policy |
| "Did my change help?" | Read the trace or AMP dashboard, compare by eye | Two runs over the same cohort, diffed |
| Getting a session | No adapter yet &mdash; import the trace you already collect | First-class for Pydantic AI, OpenAI Agents SDK, LangGraph, Mastra, Vercel AI SDK |
| Where it runs | Your process, or AMP's hosted control plane | Self-hosted server; workers replay in your environment |
