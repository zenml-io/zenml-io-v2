Hatchet is a developer platform and orchestration engine for AI agents, durable workflows, background tasks, and parallel workloads, with SDKs across Python, TypeScript, Go, and Ruby. Hatchet Cloud or self-hosted, with the full operational surface that comes with a real orchestration product &mdash; priority queues, concurrency strategies, rate limits, alerts, and OTEL export. If your durability problem is shaped like a polyglot task queue that also handles agents, Hatchet is a credible answer.

Kitaru doesn&rsquo;t orchestrate anything &mdash; it&rsquo;s a **replay-based eval layer**. It records a production run as a session &mdash; every model call, tool call, decision &mdash; and a session re-executes: unchanged, it reproduces the original as a faithful baseline; forked, it re-runs with one thing changed. Agents running on Hatchet are no exception. Wrap them with a [first-class adapter](https://docs.zenml.io/kitaru) (Pydantic AI, OpenAI Agents SDK, LangGraph, Mastra, Vercel AI SDK), or import the traces you already collect in Langfuse, LangSmith, Braintrust, or OTel, and every run becomes a session you can replay.

<FeatureWithGraphic title="Different jobs, not a competing engine">
  <RuntimeVsPlatform slot="graphic" />

  Hatchet&rsquo;s defaults are tasks, workers, queues, durable workflows, events, and schedules &mdash; a packaged orchestration platform. Kitaru&rsquo;s defaults are record, replay, and improve: wrap or import a run as a session, re-execute it with the recording answering for the world, and compare cohorts before and after a change.

  <Fragment slot="bullets">
    - **Different problems, not competing solutions.** Hatchet runs and retries your workloads. Kitaru makes your production history runnable as a test bench. Neither one does the other&rsquo;s job.
    - **Composable by design.** An agent task running inside a Hatchet workflow is exactly the kind of run Kitaru wants to record &mdash; wrap it with an adapter, or import the trace, and it&rsquo;s a session like any other.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="LLM calls as first-class session data" reverse={true}>
  <LlmLineage slot="graphic" />

  The LLM call is the unit of cost, latency, and failure in an agent. Hatchet has strong operational observability for tasks and workflows &mdash; a dashboard, alerts, metrics, and OpenTelemetry export to Datadog or Grafana. What it doesn&rsquo;t ship is a place to see the prompt, response, tokens, and cost of a specific call, linked to the run it belongs to. Kitaru&rsquo;s adapters capture exactly that on every recorded call.

  <Fragment slot="bullets">
    - **Recording, not glue code.** `KitaruAgent(agent, agent_id=AGENT_ID)` wraps a Pydantic AI agent once; every model call it makes lands as a node on the session with prompt, response, tokens, and cost.
    - **Session graph, not a generic span.** Hatchet has OTEL spans across tasks. Kitaru&rsquo;s session graph is agent-shaped: `llm_call`, `tool_call`, and `subagent_call` nodes, each carrying the fields a replay needs to reproduce it.
    - **Replay reads, not re-bills.** Replaying a session answers tool calls from the recording by default, so the LLM calls you already paid for don&rsquo;t get re-hit unless the input changed.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Replay reproduces. Experiments fork it.">
  <ReplayOverrides slot="graphic" />

  Both products replay from durable state, but they&rsquo;re answering different questions. Hatchet&rsquo;s replay resumes production work &mdash; retry this run, restart from the event log. Kitaru&rsquo;s replay reproduces a specific past run exactly, so you have a faithful baseline before you change anything. Then an experiment forks it: the same cohort, replayed again with one variable moved &mdash; model, prompt, or tool policy &mdash; and compared side by side.

  <Fragment slot="bullets">
    - **Mechanism:** `experiment.run(cohort=cohort, version="v1")` replays a cohort unchanged as the baseline; `experiment.run(cohort=cohort, version="pr-311")` replays it again against your working tree. `client.compare(before, after)` diffs the two.
    - **Use case:** The model swap you&rsquo;re considering either helps on the ten sessions that caught last month&rsquo;s regression, or it doesn&rsquo;t &mdash; and you know before you ship it, not after.
    - **What's cached:** Nothing has to be re-run to check. Both experiment runs replay the full cohort against the recording, so tool calls never touch real systems.
  </Fragment>
</FeatureWithGraphic>

## How the two surfaces map

| Concept | Hatchet | Kitaru |
|---|---|---|
| Layer | Orchestration platform (how the work runs) | Replay-based evals (how you test what it did) |
| Core unit | Task / workflow run | Session &mdash; recorded model and tool calls, re-executable |
| Composition | Workers register with the engine, triggered by tasks or events | Agent wrapped once by an adapter, or a trace imported |
| Tool calls in tests | Hit real systems, or you mock them by hand | Answered from the recording per tool policy |
| "Did my change help?" | Read the traces or dashboard, compare by eye | Two runs over the same cohort, diffed |
| Crash mid-run | Task retried by the engine | Partial session recorded &mdash; the evidence survives |
| Where it runs | Hatchet Cloud, or a self-hosted engine plus Postgres | Self-hosted FastAPI + Postgres server; workers replay in your environment |
