Braintrust tests your agent against a dataset you wrote. Kitaru tests a change against a faithful reproduction of the production runs that actually happened — tool calls and side effects included.

That difference is structural, not a feature gap. An eval platform that observed a run has the logs, but no way to stand them up again as a working environment. Scoring outputs against a dataset you picked is one job; testing a change against the real, multi-step, tool-using production history is only possible from the runtime that executed it. Kitaru executed your agent, so Kitaru can rebuild the conditions it ran in — and show you exactly what a prompt, model, or tool change would have broken.

Braintrust is very good at the job it was built for: curated datasets, custom scorers, LLM-as-judge, a prompt playground, experiments in CI. If that's the whole job for your agent, use it. The pages below are about the job it structurally can't do.

<FeatureWithGraphic title="A faithful environment rebuilt from production traces">
  Watching your agent isn't the same as being able to re-run it. Kitaru rebuilds the real conditions your agent ran in, so a change can be tested against what actually happened — not a synthetic dataset.

  <Fragment slot="bullets">
    - **Recorded as it ran:** every model call, tool call, and step boundary of a production run is captured as durable checkpoints while the agent executes. Nothing is reconstructed from logs after the fact.
    - **Re-run with one change:** replay the execution with a new model, an edited prompt, or an overridden tool result. Everything upstream of the change comes from the environment, so the change is the only difference — and the diff is attributable to it.
    - **Why only Kitaru can do this:** only the runtime that executed the agent can rebuild a faithful environment from its traces. An observability or eval tool has the logs but never executed them — it can't stand them up.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="Catch what regresses — so you can change confidently">
  The point of catching regressions isn't standing still; it's shipping the next model, prompt, or tool version without holding your breath. A refund-issuance agent that changed models should still refuse the same refunds it refused last week.

  <Fragment slot="bullets">
    - **Diff against reality:** compare the changed run to the run that actually happened — decisions, tool calls, outputs — and see exactly what regressed, and at which step.
    - **Cohorts, not cherry-picks:** re-run the change against your recent production executions, not three fixtures. The claims your triage agent actually saw are the test set.
    - **Prove it, not just fix it:** Every replay, override, and deployment is recorded as a typed, queryable audit trail. You have an answer, not a Slack thread.
  </Fragment>
</FeatureWithGraphic>

<FeatureWithGraphic title="The honest boundary">
  If your agent is a single-shot RAG answer, a dataset eval is genuinely enough. One input, one model call, one output to score — a curated dataset covers the whole behavior, and Braintrust does that job well.

  <Fragment slot="bullets">
    - **Where the environment earns its keep:** multi-step, tool-using agents — a ticket-resolution agent that reads history, calls three tools, and takes an action. The behavior lives in the trajectory, and a dataset of input/output pairs can't represent it.
    - **Many teams run both:** Braintrust scoring the single-shot components, Kitaru regression-testing changes to the agent that actually does things.
  </Fragment>
</FeatureWithGraphic>

## How the two surfaces map

| Concept | Braintrust | Kitaru |
|---|---|---|
| Test substrate | A dataset you assembled by hand | A faithful environment rebuilt from production traces |
| Unit of a test | Score vs. an expected output | Diff vs. the run that actually happened |
| Tool calls | Mocked or re-invoked inside the eval task | Reproduced from the recorded run, side effects included |
| Coverage | The cases you thought to write | The production runs that actually happened |
| Verdict | Aggregate scores per experiment | Exactly what regressed, and at which step |
| Record of a change | Experiment history | Typed audit trail linking replay → source run → change → diff |
